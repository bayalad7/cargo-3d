# 2026-11-20 — Cimientos del proyecto

## Qué se hizo

- Se analizaron alternativas (Go, Rust, Python, C#, PHP) y se eligió **Go** para todo el backend.
- Backend en Go: módulo `backend/`, servidor con apagado ordenado, ruta `GET /health`, paquete del motor
  vacío y 3 pruebas pasando (`go test`, `go vet` y `gofmt` limpios).
- Docker: `docker-compose.yml` con PostgreSQL 17 (y la API con `--profile api`), `backend/Dockerfile`
  multi-etapa con imagen final distroless sin privilegios, `.env.example`.
- Contratos independientes del lenguaje en `contracts/` (OpenAPI con `/health`) y carpeta `engine/fixtures/`.
- Documentación: `CLAUDE.md`, convenciones de Go, ADR 0001–0010, visión general, guía de Go
  comparada con PHP (capítulos 00 y 01), plan de trabajo adaptado y esta bitácora.

## Decisiones

Ver ADR 0001–0010. Resumen: **Go para todo el backend (motor y API en un binario, librería estándar),
PostgreSQL con pgx y sqlc, TypeScript para las pantallas, Wails para escritorio, Docker para la base de datos
y el despliegue.**

## Actualización de versiones

- Go 1.24 → 1.27, PostgreSQL 17 → 19, distroless debian12 → debian13, Node 22 → 26 LTS,
  pnpm 10 → 12, Turborepo 2.0 → 2.11.
- Se registraron las versiones objetivo de las tecnologías que todavía no se instalan
  (React, React Three Fiber, Vite, TypeScript, Expo, Wails, pgx, sqlc) en el ADR-0011.

## Ubicación del código de PostgreSQL

- Se definió en el ADR-0007 que todo el acceso a datos vive en `backend/internal/store`
  (`migrations/`, `queries/`, `sqlcgen/`), con `sqlc.yaml` en `backend/`. Las carpetas se crean en el sprint 2.3.
- Regla nueva en `CLAUDE.md`: solo `store` habla con PostgreSQL; `engine` nunca lo importa.

## Limpieza de Docker

- Regla nueva en `CLAUDE.md` ("Reglas de Docker"): todo lo que se cree en Docker para probar
  (contenedores, imágenes, volúmenes, redes, caché de build) se elimina al terminar, usando un proyecto
  de Compose aparte (`-p cargo3d-test`) para no tocar la base de datos de desarrollo.
  Motivo: el disco duro se llenó rápidamente con restos de Docker.

## Ramas y revisión general

- Se creó la rama `develop` para el trabajo diario; `main` queda para versiones liberadas (ADR-0012).
- Revisión de README, CHANGELOG, `docker-compose.yml`, plan y convenciones: diagrama con `internal/store`,
  sección de ramas, aviso de limpieza de Docker y CHANGELOG consolidado (aún no hay versiones liberadas).

## CI y publicación

- `main` se queda como rama por defecto de GitHub; la configuración vive en `.github/workflows/` (ADR-0013).
- `ci.yml`: a `main` solo entran `release/vX.Y.Z` o `hotfix/*`; `gofmt`, `go vet`, `go test -race` y build de la imagen.
- `release.yml`: con la etiqueta `vX.Y.Z` en `main`, publica la imagen en ghcr.io y crea el GitHub Release.
- Pendiente opcional: marcar los checks del CI como obligatorios en Settings → Rules (un workflow no puede hacerlo).

## Soporte multiplataforma

- `.gitattributes` con `* text=auto eol=lf`: mismo fin de línea en Windows y macOS.
- Dockerfile con `--platform=$BUILDPLATFORM` y `GOOS/GOARCH`: la imagen se compila de forma cruzada para
  `linux/amd64` y `linux/arm64`; CI y release construyen ambas.
- Plan: la preparación del entorno ya no exige WSL2; tabla de instalación para Windows nativo, macOS y Linux.

## Menos espacio en disco con Docker

- La caché de construcción de la imagen de la API ocupaba ~1.4 GB (sobre todo la imagen `golang`).
- Cambios: `golang:1.27-alpine` y `postgres:19-alpine`, `name: cargo-3d` en Compose, sin `restart`,
  ICU `es-MX` en PostgreSQL, `.dockerignore` más estricto, scripts `db:down`, `docker:api` y `docker:clean`,
  y la verificación de la imagen en local pasa a ser opcional (el CI ya la construye).
